# 忆桥分层情景记忆 P0/P1 PRD

状态：实施中  
日期：2026-08-13  
目标版本：schema 37+

## 1. 问题定义

当前系统完整保存 `conversation_turns`，但主要召回索引只覆盖已经晋升为
`memories` 的少量原子事实。5,000 条测试中有 2,500 条用户消息，却只对 60 条
预选消息执行提取，最终 30 条活跃记忆和 30 条 Dense 向量不能证明长期自然使用
的经历覆盖率。

产品目标从“高精度事实库”升级为“本地、分层、可追溯的长期记忆系统”：

1. 所有完成的对话都保留原始证据；
2. 所有完整问答都形成可检索情景记忆；
3. 稳定事实、偏好和指令继续使用严格版本库；
4. 稀疏行为证据可跨窗口累积后晋升；
5. 会话、日、周摘要只作为可追溯派生记忆；
6. 模型失败不得造成经历丢失或错误推进可靠水位。

## 2. 分层模型

| 层级 | 权威数据 | 用途 | 是否依赖 LLM |
|---|---|---|---|
| L0 原始会话 | `conversation_turns` | 不可替代的原始证据 | 否 |
| L1 情景记忆 | `conversation_episodes` + `memories` | 记住聊过什么、何时发生 | 否 |
| L2 行为观察 | `memory_pattern_observations` | 跨窗口累计弱信号和反证 | 提取可依赖，入账不依赖 |
| L3 语义事实 | `memory_items` / `memory_versions` | 身份、偏好、规则、关系、项目事实 | 可依赖，严格验证 |
| L4 层级摘要 | `conversation_memory_summaries` + `memories` | 会话、日、周、主题压缩 | 是，失败关闭 |

## 3. P0 范围

### P0-1 情景记忆可靠入账

- 每个完成的 user/assistant exchange 生成一条情景记忆。
- 情景正文明确区分“用户说”和“助手回答”，不得把助手回答提升为用户事实。
- 情景记忆与 user turn、assistant turn、session、owner、namespace 和 scope 双向绑定。
- 使用 turn ID 幂等；重复 outbox、Worker 重启或租约恢复不得生成重复情景。
- 凭据沿用现有落账脱敏策略。
- 原始对话事务完成后即可排队，情景生成不调用 LLM。

### P0-2 数据库与向量库联合索引

- 情景记忆进入现有 SQLite FTS5、概念倒排、ANN/Dense generation。
- FTS 在情景创建事务中立即可用。
- Dense 通过现有可重试 `index_memory` 任务异步完成。
- Dense 不可用时明确显示 degraded；不得假装完整召回。

### P0-3 统一召回

- 同一查询融合原子事实、情景记忆和层级摘要。
- 情景结果在模型上下文中标为“过往对话情景”，不得标为“已验证事实”。
- 摘要标为“派生摘要”，每条结果保留来源回溯。
- 保持 principal、role、project、session 隔离和作用域优先级。
- 事实、情景和摘要分别设配额，避免大量情景淹没稳定事实。

### P0-4 跨窗口观察累计

- 每条合格观察以 owner/namespace/scope/claim fingerprint 持久化。
- `turn_id` 唯一去重，重叠窗口不得重复计数。
- 至少三个不同 turn；可配置要求跨 session 或跨日期。
- 反例、否定、纠正和遗忘使观察衰减、阻断或失效。
- 达到门槛后只把同簇 3–5 条证据交给反思器验证。
- reflection checkpoint 是可靠提交水位；失败、截断、租约丢失不得推进。

### P0-5 反思 JSON 截断补偿

- 限制每次最多 4 个候选、每候选 3–5 条证据和字段长度。
- 记录 Ollama `done_reason`、`eval_count`、输出字符数和输出指纹。
- `done_reason=length` 或未闭合 JSON 触发一次有界重试：缩小输入与候选预算。
- 第二次失败进入现有重试/补偿链，禁止修补残缺 JSON 后提交。
- 日志记录逐候选拒绝原因。

## 4. P1 范围

### P1-1 层级摘要

- session：会话结束或空闲后生成；
- day：按用户时区聚合同一自然日；
- week：按 ISO 周聚合日摘要和必要情景；
- 摘要只覆盖可验证来源，保存来源 episode/turn ID；
- 输入指纹不变时幂等；来源变化后重建新版本；
- 摘要失败不得删除来源或覆盖上一个有效版本。

### P1-2 记忆整理

- 同一事实重复观察只增加证据，不制造重复事实；
- 情景按保留策略归档，摘要不能成为证明自身的循环证据；
- 删除会话时同步阻断相关情景和摘要召回，再由治理任务重算或清除。

### P1-3 可观测性

- 情景覆盖、FTS覆盖、Dense覆盖、摘要覆盖和观察晋升均有结构化日志；
- 召回 trace 标明每个结果来自 fact/episode/summary；
- Doctor 显示积压、失败、dead job、未索引情景和摘要来源断链。

## 5. 验收门禁

### 功能与可靠性

- 完整 exchange → episode 覆盖率：100%；
- episode user/assistant 来源绑定正确率：100%；
- FTS 覆盖率：100%；
- Worker 收敛后 Dense 覆盖率：不低于 99.9%；
- 重复 outbox、崩溃恢复后的 episode 重复率：0；
- 跨账户、跨角色、跨项目泄漏：0；
- 三条跨窗口独立证据可晋升，两个证据不可晋升；
- JSON 截断不得写入候选或推进 checkpoint；
- session/day/week 摘要来源覆盖率：100%，无来源句：0。

### 质量

- 情景固定集 Recall@5 ≥ 0.90；
- 稳定事实固定集 Recall@5 不低于改造前；
- “助手曾回答”不得被回答成“用户明确偏好”；
- 用户纠正、遗忘后旧事实复活率：0；
- 摘要事实支持率：100%。

### 性能

- 情景同步入账只执行本地事务，不调用 LLM；
- 1 万条情景下本地 FTS P95 < 150 ms；
- 可靠混合召回继续遵守现有线上门禁；
- 摘要、embedding 和反思均在后台 QoS、租约和重试约束内运行。

## 6. 非目标

- 不把每句话都晋升为稳定用户画像；
- 不用更大的云模型掩盖架构缺陷；
- 不降低三证据安全门槛制造通过；
- 不访问正式数据库、正式 3789 或私人聊天数据进行开发验收。
